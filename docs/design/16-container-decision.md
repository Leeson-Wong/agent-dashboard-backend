## 一、讨论过的核心观点

### 1. 镜像能力三层理论（源自 ChatGPT-5.2）

```
L1（可复现的 rootfs）
├─ 文件系统快照
├─ tar + checksum
└─ 可复现执行环境

L2（分层构建）
├─ Dockerfile 风格
├─ 构建缓存
└─ 可复用构建产物

L3（OCI 生态）
├─ Docker/OCI 镜像格式
├─ Registry / Tag / Pull / Push
└─ 标准化交付

结论：Docker = L1 + L2 + L3 全包
      轻量方案通常只做到 L1 或 L2
```

### 2. Docker 不是唯一答案

**Docker 的替代方案**：

| 方案 | 镜像能力(L1/L2/L3) | 隔离级别 | 复杂度 | 适用场景 |
|------|---------------------|----------|--------|----------|
| **Docker** | L1+L2+L3 | 强 | 中 | 生产环境标准化 |
| **Podman** | L1+L2+L3 | 强 | 中 | 无守护进程，更安全 |
| **LXC/LXD** | L1 | 中 | 低 | 系统级容器 |
| **systemd-nspawn** | L1 | 低 | 低 | 原生进程隔离 |
| **Supervisor** | 无 | 无 | 低 | 进程管理 |

### 3. 构建与运行时可以解耦

```
传统思维：
Dockerfile → Docker daemon → Container

解耦思维：
构建工具（Buildah）→ OCI 镜像 → 运行时（Podman/nspawn/bwrap）

优势：
- 更灵活的组合
- 避免 Docker daemon 的安全风险
- 可以选择最轻量的运行时
```

## 二、已记录的关键技术方案

### 方案 A：Docker Compose（容器化）

**优势**：
- ✅ 环境一致性
- ✅ 资源隔离
- ✅ 生态成熟

**劣势**：
- ❌ Docker 守护进程开销
- ❌ 安全攻击面
- ❌ 存储和网络复杂性

**适用**：中大规模生产环境

---

### 方案 B：Podman（无守护进程容器）

**优势**：
- ✅ 完全兼容 Docker 镜像（OCI）
- ✅ 无守护进程，更安全
- ✅ Rootless 模式
- ✅ 可以作为 systemd 服务运行

**劣势**：
- ⚠️ 生态相对较小
- ⚠️ Windows 支持有限

**适用**：安全敏感的 Linux 生产环境

---

### 方案 C：Systemd Services（进程级）

**优势**：
- ✅ Linux 原生，最简单
- ✅ 零额外开销
- ✅ 集成 journald 日志
- ✅ 自动重启策略

**劣势**：
- ❌ 无隔离
- ❌ 环境依赖管理复杂
- ❌ 跨平台差

**适用**：单机、小规模、开发/测试

---

### 方案 D：Supervisor（跨平台进程管理）

**优势**：
- ✅ 跨平台（Linux/macOS/Windows）
- ✅ 进程管理
- ✅ Web UI

**劣势**：
- ❌ 隔离性差
- ❌ 需要额外安装

**适用**：开发/测试、跨平台小规模部署

---

### 方案 E：Serverless（Lambda 等）

**优势**：
- ✅ 零运维
- ✅ 按需付费
- ✅ 自动扩缩容

**劣势**：
- ❌ 冷启动延迟
- ❌ 执行时间限制（15分钟）
- ❌ 状态管理复杂

**适用**：事件驱动、间歇性任务

## 三、当前项目的关键需求分析

### 已明确的需求

1. **分布式 Agent**：
   - 每个 Agent 可能在独立容器/进程中
   - 需要跨容器通信
   - 需要透明代理机制

2. **保留原生能力**：
   - 不修改 CrewAI 等开源框架
   - 保留 Agent 的智能决策能力
   - 保留原生协商机制

3. **可部署性**：
   - 支持水平扩展
   - 支持动态添加/移除 Agent
   - 支持多语言 Agent

### 暂不确定的需求

- 部署规模（单机 vs 集群）
- 运维能力（是否有专职运维）
- 安全要求（企业级 vs 开发测试）
- 资源限制（CPU/内存/GPU）

## 四、推荐的决策路径

### 阶段 1：原型验证（当前）

**目标**：验证分布式 Agent 架构

**推荐方案**：
```
├─ Systemd Services（本地开发）
├─ Supervisor（跨平台测试）
└─ 直接 Python 进程（最简单）

无需容器化，专注于验证架构设计
```

### 阶段 2：小规模部署（1-10 个 Agent）

**推荐方案**：
```
选项 1：Systemd + 虚拟环境
├─ 最简单
├─ 足够用
└─ 易于调试

选项 2：Docker Compose
├─ 环境一致性
├─ 一键部署
└─ 团队协作
```

### 阶段 3：中等规模（10-50 个 Agent）

**推荐方案**：
```
├─ Podman（获得容器化 + 镜像能力）
├─ Systemd 集成（作为服务管理）
└─ Redis 消息队列

优势：
✅ 比 Docker 更安全（无守护进程）
✅ 完整的 OCI 镜像支持
✅ 可以 rootless 运行
```

### 阶段 4：大规模（50+ 个 Agent）

**推荐方案**：
```
├─ Kubernetes（如果需要自动扩缩容）
└─ 或继续 Podman + Systemd（如果规模可控）

考虑：
- 运维团队规模
- 是否需要自动扩缩容
- 是否需要滚动更新
```

## 五、基于"镜像能力三层"的技术选型

### 如果需要 L1+L2+L3（完整镜像能力）

| 组件 | 推荐方案 | 说明 |
|------|----------|------|
| **构建工具** | Buildah | 替代 Dockerfile，兼容 OCI |
| **运行时** | Podman | 无守护进程，安全 |
| **编排** | Systemd | 与系统集成 |
| **或** | Docker Compose | 如果团队熟悉 Docker |

### 如果只需要 L1（rootfs 快照）

| 组件 | 推荐方案 | 说明 |
|------|----------|------|
| **构建** | debootstrap / apk | 系统级镜像 |
| **运行时** | systemd-nspawn | 原生容器 |
| **隔离** | User namespaces | 轻量级隔离 |

### 如果需要混合方案

```
构建层：Buildah（生成 OCI 镜像）
运行层：Podman 或 systemd-nspawn
管理层：Systemd 或 Supervisor
```
